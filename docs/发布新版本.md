# 发布新版本 · 傻瓜手册

这份文档假设你不写代码。照着做就行，每一步都有「成功是什么样」。

---

## 零、先理解一件事

以前构建老是失败，根本原因只有一个：

> **源码、题库数据、前端资源都不在仓库里，每次构建都要临时去网上下载。**

而那些下载链接会过期（源码的那个签名链接 **2026 年 11 月 19 日** 就失效）、会变更、
会因为对方调整而 404。任何一个环节断了，构建就红一片。

现在这些东西全部躺在仓库里了，构建过程**不需要联网下载任何东西**。
所以「链接过期导致构建失败」这类问题从此不会再有。

---

## 一、一次性准备（只做一次）

### 1. 装 Node.js

打开 https://nodejs.org/ 下载 **22 LTS** 版本，双击安装。装完不用管。

验证：打开「终端」，输入

```bash
node -v
```

看到 `v22.x.x` 就成了。

### 2. 确认 git 能连 GitHub

你之前推送过代码，应该已经配好了。验证：

```bash
cd ~/你的仓库目录
git remote -v
```

能看到 `github.com/william001207/quanzhi-kaoyan-desktop` 就对了。

### 3. 第一次把新仓库推上去

如果你拿到的是一个已经整理好的仓库目录（含源码、数据、前端资源），执行：

```bash
cd ~/仓库目录
bash scripts/setup-repo.sh
```

这个脚本会：检查文件是否齐全 → 本地提交 → 打上 v1.0.0 tag。
**它不会推送**（见下面第 4 步，推送统一走 GitHub Desktop）。

---

## 二、以后发新版：四步

### 第 1 步：改版本号

打开 `package.json`，把这一行的数字改大：

```json
"version": "1.0.0"
```

改成 `1.0.1`（小修改）、`1.1.0`（加了新功能）、`2.0.0`（大改动）。
**只改数字，不要改别的。**

### 第 2 步：本地提交并打 tag

这一步在你自己机器上完成，**不需要网络、不需要账号密码**：

```bash
cd ~/仓库目录
git add -A
git commit -m "release: v1.0.1"
git tag v1.0.1
```

> tag 名字必须和 `package.json` 里的版本号一致（`v` + 版本号）。

以前这里还会写 `git push` 和 `git push --tags`，现在**不写了**：
这台机器上没有配推送凭证，`git push` 一定会失败（报 `could not read Username`）。
推送统一走下一步的 GitHub Desktop。

### 第 3 步：打开 GitHub Desktop，点 Push origin

⚠️ **顺序死规则：必须先把 main 推上去，再去网页建 Release。**

打开 GitHub Desktop，选中这个仓库，右上角点 **Push origin**。
看到它显示「No local changes」、和远端已同步，就说明推成功了。

为什么顺序不能反：网页上建 Release 时，GitHub 会拿**当时 main 指向的那个提交**来新建 tag。
如果 main 还没推，tag 就落在上一个提交上，自动构建会用旧代码打包 ——
表面 Release 写着新版本，产物却是老版本的安装包（v1.2.3 就这么踩过一次）。

> GitHub Desktop **不会推送 tag**，这是正常的。tag 在下一步的网页上新建。

### 第 4 步：网页建 Release，触发自动构建

1. 打开仓库的 **Releases** 页面，点 **Draft a new release**
2. **Choose a tag** 输入 `v1.0.1`，下拉里选「Create new tag: v1.0.1 on publish」
3. **Target** 选 `main`（此时 main 就是刚推上去的那个提交）
4. 标题填 `v1.0.1`，正文按下面说的方法粘贴
5. 点 **Publish release**

**成功的样子**：点完 Publish，Actions 页面会出现一个新的 `build` 任务，
大约 3–15 分钟后两个任务都变绿，这个 Release 里就出现新的安装包：

- `quanzhi-kaoyan-1.0.1-mac-arm64.dmg`
- `quanzhi-kaoyan-1.0.1-win-x64.exe`

下载对应的那个装上就行。Windows 包通常先出来，macOS 的构建机经常要排队几分钟，
**只看到一个包是正常的**，等另一个跑完会自动补进同一个 Release。

#### 正文从哪里来

上面第 4 点要粘贴的文字，**不用自己想**，仓库里已经存好了：

> 打开 `docs/Release正文.md`，找到对应版本那一节，
> **从 `## 更新内容` 那行开始复制，到该节最后一行**，粘贴进去即可。
> 不要带上 `## v1.1.3` 这层标题，也不要带其它版本的内容。

新版本还没有正文的话，让 AI 按那一节顶部的模板写一段，追加进去。

## 三、如果你的 Mac 上直接构建（不走 GitHub）

GitHub 的 macOS 构建机是远程的，有时可能要排队。你本机就是 Mac，
也可以直接本地出 dmg，更快：

```bash
cd ~/仓库目录
bash scripts/build-desktop.sh mac
```

跑完 `release/` 目录里就有 dmg，双击安装即可。
**这个方式产出的包已经做过 ad-hoc 签名**，可以直接用。

## 四、出问题怎么查（按这个顺序看）

### 构建失败，Actions 里某个步骤红叉

点开红色那一步看日志。常见的三种：

| 报错里出现 | 说明 | 怎么办 |
|---|---|---|
| `自检未通过` / `[失败] 缺少文件` | 仓库缺文件 | 按日志列出的文件名去补，然后重新 commit |
| `Cannot find module` | 依赖没装上 | 检查 `package-lock.json` 是否提交了 |
| `tsc` 报错 + 文件名 | 代码有语法错误 | 把完整报错发给 AI，让它改那个文件 |

### 安装后打开就闪退 / 窗口白屏

以前这种情况你完全看不到原因，现在会**弹窗告诉你**：
- 「启动失败：找不到服务端程序」→ 安装包不完整，或本地没编译
- 「启动失败：本地服务没能起来」→ 数据库或端口问题，弹窗里有具体建议

按弹窗里的提示处理。如果还不行，把弹窗内容发给 AI。

### macOS 提示「已损坏」或「无法验证开发者」

未签名的正常现象，任选一种：

1. 右键点应用 → 「打开」→ 再点「打开」
2. 系统设置 → 隐私与安全性 → 点「仍要打开」
3. 终端执行（最彻底，之后就正常了）：

```bash
xattr -dr com.apple.quarantine "/Applications/全职高手考研系统.app"
```

## 五、更新题库数据

题库在 `server/data-export/` 目录，22 个 JSON 文件，**随安装包分发**。

先明确一件事：**应用不联网，不存在「检查题库有没有更新」这回事。** 只有下面两条路。

### 情况 A：加少量新题（推荐，不用重新打包）

用应用内的「数据导入」功能，导入大纲/章节和真题，直接写进你本机数据库。
**立即生效，不用改代码、不用重新打包、不用发版。**

### 情况 B：整批换题库快照（必须重新打包）

1. 把新文件覆盖到 `server/data-export/`
2. **必须**同时修改 `server/database/local-db.ts` 里的这一行：

```ts
const DATA_VERSION = '2026-10-20.1';   // ← 改成新值，比如 '2026-11-05.1'
```

3. 重新打包并安装（本地双击，或推 tag 走 GitHub）

第 2 步是「版本对齐」的开关：新安装包启动时发现这个值跟你本地库记录的不一样，
才会用包里的数据刷新题库内容。**版本没变就什么都不做。**

- 改了版本号但没换数据 = 白刷一次
- 换了数据但没改版本号 = 新数据永远不会生效

> ⚠️ 一个版本号只能对应一份数据。用旧数据打新包，内容会被回退成旧数据
> （你的学习进度不会丢，但题库内容会变旧）。

## 六、万一改坏了想退回

每一次提交都是一个还原点。退回上一个版本：

```bash
git log --oneline -5          # 看看最近 5 次提交
git revert <那次的编号>        # 撤销某次改动，会生成一个新的提交
```

撤销完，在 GitHub Desktop 点 **Push origin** 推上去。

> **不要用 `git reset --hard`，也不要用 `git push --force`。**
> 这两条会直接把历史抹掉：已经被撤销的提交找不回来，已经推到 GitHub 的内容强推之后，
> 仓库和你本机的记录就对不上了，后面想排查「哪次改动弄坏的」会彻底失去线索。
> 要退版本，就用上面的 `git revert`（它只新增一个提交，不改历史），
> 或者直接告诉 AI「帮我退到某次提交」，让它处理。

> 大面积改代码前，可以先打个备份点：`git tag backup-$(date +%Y%m%d)`，
> 出问题能一键回到改之前。

## 七、你想改功能时该怎么跟 AI 说

既然是靠 AI 改代码，说话方式很影响结果。建议这个格式：

```
【改什么】错题本页面加一个「按科目筛选」的下拉框
【为什么】错题太多，想只看口腔解剖的
【不能动】不要改数据库表结构；不要动复习算法
【验收】筛选后列表只显示该科目的错题，刷新后保持
```

最后一条最重要：**明确说出「不能动什么」**。
比如「不要改 `server/database/schema.sql`」，AI 就不会去碰表结构，
你本机数据库也就不会被搞坏。

如果某次改动**必须**加数据库字段，一定要先跟 AI 强调：

```
这次要加字段。请同时给我一个迁移脚本，
保证我现有数据库里的学习进度不丢。
```

否则新版本启动时会因为「表里没这一列」直接报错——这是这类应用最容易踩的坑。
